# 파츠 합성 프리뷰 툴

`SnailData.xlsx` + `Resource/` 를 그대로 읽어서 달팽이 조합 결과를 눈으로 확인하고,
부화 추첨 로직과 데이터 정합성을 Unity 붙이기 전에 검증하는 도구입니다.

## 사용법

1. **데이터 갱신** — `SnailData.xlsx` 를 수정한 뒤 아래를 실행합니다. (Excel 이 켜져 있어도 됩니다.)

```bash
powershell -ExecutionPolicy Bypass -File Tools/ExportSnailData.ps1
```

2. **열기** — `Tools/preview/index.html` 을 브라우저로 엽니다. 서버 불필요, `file://` 로 동작합니다.

## 탭 구성

| 탭 | 하는 일 |
|---|---|
| **조합기** | 파츠·색상을 직접 골라 합성 결과 확인. 레이어 순서를 바꿔가며 z-order 검증 |
| **부화 시뮬** | EggData 기준으로 N마리 부화. 카드를 클릭하면 그 조합이 조합기로 넘어감 |
| **확률 분포** | 대량 추첨(기본 2만회) 후 파츠별 실제 출현 빈도 집계 |
| **파츠 아틀라스** | PartsData 전 행을 단독 렌더링. 리소스/색상 매핑 오류가 즉시 보임 |
| **데이터 검증** | 리소스 누락, Id 충돌, 색상 타입 불일치, 그룹 완결성 점검 |

## 리소스 규약 (툴이 전제하는 것)

- 모든 파츠 PNG 는 **1200×1200 공유 캔버스**에 미리 배치 → 오프셋 없이 순수 z-스택 합성
- 선화 레이어: `Resource/{PartsType}/{ResourceKey}.png`
- 색상 레이어: `Resource/{PartsType}/Color/{ColorResourceKey}.png`
- 파츠 1개 = **색상 레이어(아래) + 선화 레이어(위)** 2장
- **색상 레이어는 선화 전용입니다.** `commonshell01_c*` 는 `commonshell01` 에만 맞고,
  `commonshell02` 에 씌우면 실루엣이 달라 색이 윤곽 밖으로 삐져나옵니다.
  조합기의 `타입 내 모든 색상 허용` 체크박스를 켜면 이 현상을 직접 확인할 수 있습니다.
  (현재 `PartsData` 는 이 규칙을 모두 지키고 있습니다.)
## 레이어 순서 (z-order)

기본값 (뒤→앞): `Mucus → Feeler → Body → Shell → Eyes`
— 더듬이 밑동이 몸통 뒤로 숨고, 껍질이 몸통 위에 얹히고, 눈이 최상단.

이 순서는 **`EnumData` 의 `SortOrder` 열(nullableint)** 에서 읽습니다.
열이 없거나 일부만 채워져 있으면 위 내장 기본값으로 폴백합니다
(부분 입력을 신뢰하지 않습니다 — 절반만 채운 상태로 조용히 이상한 순서가 나오는 걸 막기 위함).

권장 값 — 간격 100은 나중에 사이에 끼워 넣기 위한 여유입니다:

| EnumType | EnumName | SortOrder |
|---|---|---|
| PartsType | Mucus | 100 |
| PartsType | Feeler | 200 |
| PartsType | Body | 300 |
| PartsType | Shell | 400 |
| PartsType | Eyes | 500 |
| AccessoriesType | Bag | 600 |
| AccessoriesType | Hat | 700 |

- **`EnumValue` 를 순서로 재활용하지 마세요.** EnumValue 는 직렬화 ID 라 세이브 데이터와 묶여
  있어 배포 후 변경이 불가능한 반면, 노출 순서는 아트를 보며 자주 조정하는 값입니다.
- 악세서리(Hat/Bag)는 시트가 다르지만 같은 z-스택에 끼어들어야 하므로 **같은 숫자 축**을 씁니다.
  배열이 아니라 숫자여야 하는 이유가 이것입니다.
- 파츠별 개별 오버라이드(`PartsData.SortOrderOffset`)는 아직 넣지 않았습니다.
  현재 파츠 중 타입 기본값에서 벗어나야 하는 예외가 0건입니다.
- **오름차순이 뒤 → 앞입니다.** 값이 작을수록 뒤로 갑니다.
  `Eyes` 를 `Body` 보다 작게 주면 눈이 몸통 색에 완전히 가려져 얼굴이 텅 빕니다.
  검증 탭이 이 조합을 오류로 잡습니다.

조합기 탭에서 순서를 바꾸면, 그 순서를 `SortOrder` 에 그대로 옮겨 적을 값이 표로 나옵니다.

## 부화 추첨 로직

1. `EggData.PartsGroupIds` 에 적힌 **모든 그룹의 파츠를 하나의 풀로 합칩니다** (union)
2. 그 풀에서 `PartsType` 별로 `AppearWeight` 가중 추첨
3. 뽑힌 파츠의 `Colors` 중 1개 선택

즉 그룹은 **누적 해금** 개념입니다. `[레어알01]` 은 `[일반그룹] + [레어그룹]` 을 합친
풀에서 뽑으므로, 레어그룹에 껍질만 있어도 몸·눈·더듬이는 일반그룹에서 채워집니다.
개별 그룹이 일부 파츠만 갖는 것은 정상입니다.

> 기획서 「개발 명세」 에는 `1. EggData의 PartsGroupIds 중 1개 ID 무작위 선택` 이라고
> 적혀 있는데 이는 실제 사양과 다릅니다. 기획서 문구를 고쳐주세요.
> `그룹 선택` 드롭다운의 `그룹 1개 무작위` 는 그 옛 문구대로 돌려보는 비교용 옵션입니다.

## 검증 탭이 잡는 것

- 리소스 존재 — 파츠 선화·색상, 알 이미지
- `Id` 중복, 빈 `PartsGroupId`, 뽑히지 않는 `AppearWeight`
- 색상 타입 불일치, 선화와 색상의 접두사 어긋남, 참조되지 않는 색상·리소스
- **그룹 완결성** — 그룹이 단독 선택됐을 때 빠지는 부위가 있는지
- **`SortOrder` 정합성** — 값 중복(앞뒤 비결정), 일부만 채워 폴백되는 상태,
  눈이 몸통 뒤로 가는 조합, 악세서리가 껍질에 가리는 조합
- **시트 간 `Id` 참조 무결성** — `ShopData` / `GachaData` / `EventData` 가
  삭제된 아이템을 붙들고 있는지

## 알려진 데이터 이슈

- **`[일반_일반더듬이]` Id 가 29·30행에 중복** → Id 키 딕셔너리에서 한 행이 유실됩니다.
- **`ShopData` 10·11행, `GachaData` 10·11행이 삭제된 `[에픽알01]` / `[레전더리알01]` 을
  아직 참조**합니다.
- **`Hat` 과 `Bag` 의 SortOrder 가 둘 다 250** → 서로의 앞뒤가 비결정적입니다.
- `PartsColorData` 의 Eyes 2종·Mucus 2종은 파일 없이 정의만 남아 있습니다.
  (Eyes 는 `IsUseColor=0` 이라 무해, Mucus 는 파츠 자체가 아직 없음)
